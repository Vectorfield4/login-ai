Внедрение генеративного AI в корпоративную аналитику долгое время шло по тупиковому пути прямой генерации кода (Text-to-SQL) одной монолитной языковой моделью. На практике этот подход сталкивается с тремя барьерами: галлюцинации в enterprise-метриках, риск SQL-инъекций и высокая стоимость запросов при обработке простых диалоговых фраз дорогой моделью.

Эффективное решение этих проблем — переход к мультиагентным системам с разделением ответственности и детерминированным контрактом данных. Ниже представлена архитектура Conversational BI, построенная по схеме Intent LLM, Smart LLM, Semantic Layer и Data Analysis Layer.

## Обзор концептуальной архитектуры

Архитектура распределяет нагрузку между узкоспециализированными компонентами. Одна модель не справляется одновременно с диалогом, контекстом, структурой базы и генерацией кода. Система делит эти задачи на два слоя LLM и программную обвязку.

```text
       [ Пользователь ]
               │
               ▼ (1. Живой язык: "Какая выручка по застройщику YoY?")
┌──────────────────────────────────────────────┐
│          1. Слой Диспетчеризации             │
│                (Intent LLM)                  │
├──────────────────────────────────────────────┤
│ • Память контекста и сессии пользователя     │
│ • Бизнес-ограничения темы (Локальный RAG)    │
│ • Реестр возможностей (Capabilities)         │
└──────────────────────┬───────────────────────┘
                       │
                       ▼ (2. Маршрутизация: только аналитический интент)
┌──────────────────────────────────────────────┐
│            2. Слой Аналитики                 │
│                (Smart LLM)                   │
├──────────────────────────────────────────────┤
│ • Валидация входных сущностей                │
│ • Выделение метрик, разрезов, фильтров       │
│ • Генерация Structured Output (Strict JSON)  │
└──────────────────────┬───────────────────────┘
                       │
                       ▼ (3. Детерминированный JSON-контракт)
┌──────────────────────────────────────────────┐
│           3. Семантический слой              │
│            (Semantic Layer / API)            │
├──────────────────────────────────────────────┤
│ • Валидация комбинаций параметров            │
│ • Динамическая сборка безопасного запроса    │
│ • Оркестрация Data Analysis Layer            │
└──────────────────────┬───────────────────────┘
                       │
                       ▼ (4. Безопасный SQL / Выполнение в DWH)
┌──────────────────────────────────────────────┐
│         4. Слой хранения и расчета           │
│             (Data Storage & OLAP)            │
└──────────────────────────────────────────────┘
```

## Детальный разбор слоев и зон ответственности

### 1. Слой диспетчеризации (Intent LLM)
Этот слой работает как фронт-офис системы. Его задача — фильтровать входящий поток запросов и удерживать контекст беседы. 

* **Класс модели:** Легковесная и быстрая модель с низкой стоимостью токена (GPT-4o-mini или Llama-3-8B).
* **Память сессии:** Хранит историю переписки. Если пользователь сначала спросил про Москву, а потом написал «а по застройщику?», Intent LLM соединяет запросы в один контекст.
* **База знаний (RAG):** Содержит инструкции о темах, на которые система отвечать не должна.
* **Реестр возможностей:** Содержит верхнеуровневый список инструментов. Модель знает, что система работает с аналитикой, но не хранит имена таблиц или колонок.
* **Логика работы:** При обычном приветствии или смолл-токе модель отвечает сама. При обнаружении аналитического интента модель вызывает инструмент (Tool Calling) и передает задачу на второй слой.

### 2. Слой аналитики (Smart LLM)
Бэк-офис системы, изолированный от пользователя. Его единственная задача — переводить живую речь в жесткую структуру данных.

* **Класс модели:** Тяжелая модель с развитым логическим мышлением (GPT-4o или DeepSeek-V3), настроенная на генерацию Structured Output.
* **Извлечение сущностей:** Модель делит запрос пользователя на составные части куба данных:
    * **Метрики:** Выручка, прибыль, EBITDA, продажи.
    * **Разрезы:** Город, регион, застройщик.
    * **Фильтры:** Метро рядом (true), дата стройки (> 2024), сдан (false).
    * **Сравнения:** Год к году (YoY), месяц к месяцу (MoM).
* **Выходной контракт:** На выходе формируется только валидный JSON по строгой схеме без свободного текста.

### 3. Семантический слой (Semantic Layer)
Критический компонент на классическом бэкенд-коде без использования ИИ. Он отвечает за безопасность и бизнес-логику.

* **Регистрация при запуске:** При старте бэкенд сканирует базу данных и загружает матрицу разрешенных параметров.
* **Валидация бизнес-логики:** Проверяет полученный от Smart LLM JSON на совместимость параметров. Если метрику выручки пытаются посчитать в неверном разрезе, семантический слой прерывает запрос до обращения к базе.
* **Безопасность:** Доступ модели к структуре базы данных закрыт, она оперирует абстрактными терминами. Семантический слой сам собирает безопасный параметризованный SQL-запрос.

### 4. Слой анализа и хранения данных (Data Analysis Layer)
Финальный этап агрегации. Семантический слой отправляет безопасный запрос в DWH или OLAP-куб (ClickHouse, PostgreSQL, Greenplum) и получает сырой массив данных.

## Жизненный цикл одного запроса (Data Flow)

Рассмотрим обработку аналитического запроса в динамике:

1. **Пользователь пишет в чат:** «Какая выручка по застройщику в Москве в сравнении год к году?»
2. **Intent LLM** определяет аналитический интент, собирает контекст и передает очищенный запрос на второй слой.
3. **Smart LLM** анализирует текст и выдает JSON:
    ```json
    {
      "metrics": "Revenue",
      "dimensions": ["zastroyshik"],
      "filters": [
        {"field": "city", "operator": "EQUALS", "value": "Moskva"}
      ],
      "comparison": "YoY"
    }
    ```
4. **Семантический слой** проверяет JSON по матрице правил, собирает безопасный SQL-шаблон и отправляет его в базу данных.
5. **База данных** выполняет расчет и возвращает цифры: `[{zastroyshik: "ПИК", revenue_2025: 100M, revenue_2026: 112M, change: +12%}]`.
6. **Обратный поток:**
    * Данные возвращаются в **Smart LLM**, которая формулирует текстовый инсайт («В Москве выручка застройщика ПИК выросла на 12% год к году...») и указывает тип UI-компонента (`{"ui_component": "LineChart"}`).
    * **Intent LLM** отправляет пользователю готовый виджет с графиком и пояснением.

## Архитектурные преимущества подхода

* **Предсказуемость цифр:** Модель передает семантическому слою параметры выборки. Она не вычисляет значения самостоятельно, поэтому не генерирует галлюцинации. При неверном запросе система возвращает ошибку.
* **Экономия бюджета (TCO):** Около трети сообщений в корпоративных чатах — это приветствия, уточнения или опечатки. Обработка таких запросов дешевой Intent LLM экономит до 60% бюджета на токены.
* **Изоляция базы данных:** Прямой доступ языковой модели к выполнению команд в СУБД закрыт, что исключает риск SQL-инъекций.
* **Масштабируемость:** При изменении структуры базы данных не нужно переобучать или заново промптить LLM. Достаточно обновить маппинг в семантическом слое.
